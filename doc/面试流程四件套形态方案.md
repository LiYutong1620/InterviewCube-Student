> **状态**：✅ **方案已拍板（方案 A）** —— 施工进度见 §七，**S1 / S2 / S3 / S4 / S5 全部落地**
> **最后更新**：2026-09-22

## 一、先说结论

**这四个模块不是 4 个独立的 CRUD 表格，而是同一条面试流程的 4 个环节。**

推荐 **方案 A**：以「**场次**」为主干，另外三页从场次**下钻**；**不动 `sys_menu`**，靠路由参数把四页串成一条链路。

理由：

- 学生的心智模型是「我要练一次面试 → 答完 → 看报告 → 回看历史」，不是「我要管理 4 张表」
- 四张表本来就是**父子关系**（下面 §2.1），拆成 4 个平级菜单，学生进来根本不知道该先点哪个
- **不动 `sys_menu`** 这一点很关键：菜单已绑 49 条（§4.6），且三端合并约定菜单 id 段（2000~2048）不能乱动 —— 靠路由参数串联可以完全避开这个风险

## 三、方案对比

| | **方案 A：场次为主干**（推荐） | 方案 B：4 页各自只读 | 方案 C：合并成一个 Tab 页 |
| :--- | :--- | :--- | :--- |
| 菜单 | **不动**（4 个菜单保留） | 不动 | **要动**（4 个合 1 个，删 3 个菜单） |
| 串联方式 | 路由参数 `?sessionId=x` | 无（学生自己找） | Tab 切换 |
| 学生体验 | 一条链路，跟着走就行 | 割裂，不知道该点哪个 | 一条链路，但四张表挤在一页 |
| 外键手填框 | 去掉，由路由带入 | 去掉后**无从下钻**（没地方带 `sessionId`） | 去掉，由 Tab 内部状态带入 |
| 工作量 | 中（4 页改造 + 少量后端） | 小（4 页各自删按钮） | 大（要重做菜单 + 页面重构） |
| 三端合并风险 | **低** | 低 | **高**（动了 `sys_menu`） |

**方案 B 的致命问题**：把「所属面试场次ID」手填框去掉（这是 §5.1 的硬要求）之后，学生**没有任何入口**能定位到「某一场的题目」，页面就废了。

**方案 C 的问题**：必须改 `sys_menu`（4 个菜单合并），而菜单是共享面；而且 `report` 的数据量（雷达图 + 长文本）塞进 Tab 会让页面很重。

**→ 推荐方案 A。**

## 四、方案 A 的详细形态

### 4.1 流程总览

```
首页「开始面试」
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│ ① /student/session   历史面试记录（主干）                │
│    「开始面试」按钮 → 选岗位画像 + 题型 + 题目数          │
│    → 生成场次（status=进行中）+ 从题库抽题               │
└─────────────────────────────────────────────────────────┘
      │ 行内操作（按 status 变化）
      ├── 未开始 / 进行中 ──►「继续作答」
      │        ▼
      │   ┌──────────────────────────────────────────┐
      │   │ ③ /student/qa?sessionId=x   作答页        │
      │   │   逐题作答；参考答案隐藏（决策 1）         │
      │   │   全部答完 → status=已完成 + end_time     │
      │   └──────────────────────────────────────────┘
      │        │ 完成后
      ├── 已完成 ──►「查看报告」
      │        ▼
      │   ┌──────────────────────────────────────────┐
      │   │ ④ /student/report?sessionId=x  复盘报告   │
      │   │   总分 + 五维雷达图 + 薄弱点 + 建议        │
      │   └──────────────────────────────────────────┘
      │
      └── 已完成 ──►「回顾题目」
               ▼
          ┌──────────────────────────────────────────┐
          │ ② /student/question?sessionId=x  题目回顾  │
          │   题目 + 我的作答 + 参考答案（此时才可见） │
          └──────────────────────────────────────────┘
```

> ② ③ ④ 三页**都必须从 ① 带 `sessionId` 进来**；直接点菜单进来时，显示一个「请先从『模拟面试场次』选择一场面试」的空态 + 一个场次下拉。

### 4.2 四个页面逐个说明

#### ① `/student/session` —— 历史面试记录（主干）

**形态**：列表 + 分页 + 「开始面试」对话框 + 行内操作。**去掉裸 CRUD 的新增/修改弹窗。**

| 项 | 内容 |
| :--- | :--- |
| 查询区 | **状态**（字典 `interview_session_status`）+ **岗位名称**（模糊）。去掉「场次编号」「开始/结束时间」 |
| 列表列 | 场次编号 / 岗位名称 / 难度(dict-tag) / 题型(dict-tag) / **进度**（`已答/总题`） / 状态(tag) / 本场总分 / 开始时间 / 操作 |
| 去掉的列 | 主键ID / 所属学生用户ID / 关联岗位画像ID / 创建者 / 更新者 / 更新时间 |
| 行内操作 | `未开始`/`进行中` → **继续作答**；`已完成` → **查看报告** + **回顾题目**；所有行 → **删除** |

**「开始面试」对话框**（替代原「新增」按钮）：

| 字段 | 控件 | 说明 |
| :--- | :--- | :--- |
| 目标岗位 | `el-select`，来源 = **自己的岗位画像列表**（`student_job_profile`） | 选中后带入行业/岗位名/难度 |
| 题型 | `el-select`，字典 `interview_question_type` | 可多选，默认全选 |
| 题目数 | `el-input-number`，默认 5 | 上限 20 |

后端在 `insert` 时生成：`session_no`（如 `S20260922143012 + 3 位随机`）、`user_id`（`bindOwner`）、
`industry` / `job_name` / `difficulty`（从岗位画像带入）、`status = '1'`（进行中）、`start_time = now()`。
**这些字段前端一律不传。**

#### ② `/student/question?sessionId=x` —— 题目回顾

**形态**：只读列表 + 详情抽屉。**去掉新增 / 修改 / 删除按钮、去掉手填的外键框。**

| 项 | 内容 |
| :--- | :--- |
| 查询区 | **去掉**（该场的题目一共就几道，且已由 `sessionId` 限定） |
| 列表列 | 题号 / 题型(dict-tag) / 题干(tooltip) / 来源(dict-tag) / **我的作答**（有/无） / 操作（查看） |
| 详情抽屉 | 题号 / 题型 / 题干 / **参考答案 + 关键要点（按决策 1 门控）** / 我的作答 |

**参考答案的显隐判据（决策 1 落地）**：
`session.status === '2'`（已完成）**或**该题在 `interview_qa` 里已有记录 → 显示；否则显示「提交后可见」的占位。

#### ③ `/student/qa?sessionId=x` —— 作答页

**这是唯一有写操作的页面**，也是整条链路的「心脏」。

| 状态 | 形态 |
| :--- | :--- |
| 场次 `进行中` | **逐题作答模式**：顶部场次信息 + 进度；主体是当前题卡片（题号 + 题干）+ 作答文本域 + 「提交并下一题」；底部题号导航（已答/未答）。参考答案隐藏 |
| 场次 `已完成` / `已中断` | **只读回顾模式**：题干 + 我的作答 + 参考答案（此时可见）+ 本题得分（阶段一为空） |

- 提交作答 → 后端 `insert` 或 `update` `interview_qa`，**只允许改** `answer_content` / `answer_type` / `answer_time` / `duration`
- **必须校验场次 `status = '1'`**，已完成/已中断的场次不允许再写（防前端绕过）
- 全部题目答完 → 后端把场次置为 `status = '2'`、写 `end_time`、算 `duration`
- 阶段一只做**文字作答**（`answer_type = '1'`），语音/视频选项先禁用（`audio_url` / `video_url` 不启用）

#### ④ `/student/report` —— 复盘报告

| 项 | 内容 |
| :--- | :--- |
| 列表 | 报告编号 / **关联场次**（显示「岗位名 + 开始时间」而不是裸 `sessionId`） / 总分 / 生成状态(tag) / 生成时间 / 操作（查看） |
| 查询区 | 生成状态 + 岗位名称。去掉「报告编号」「关联面试场次ID」 |
| 详情 | ✅ S4：**总分**（大字） + **五维雷达图**（`echarts` 5.6.0） + 五个维度的分数条 + **总结** / **薄弱点**（`weak_points` JSON 数组 → 标签） / **改进建议** + PDF 下载（阶段一不生成，按钮先留好） |
| 空态 | ✅ S4：`generate_status = '0'` / `'1'` → 显示「报告生成中，稍后回来看看」；`'3'`（失败）→ 显示「报告生成失败，可以重新生成」+「手工填分」按钮 |

`interview_session.report_id` 作为**冗余指针**由后端在生成报告时一并写入，只用于列表页快速取报告。
不要出现「只写一边」的情况。

✅ **S4 已按此落地**：`InterviewSessionServiceImpl.refreshSessionProgress` 建完报告壳后顺手写 `session.report_id`
（值相同则不写，省一次 update），两边永远一致。详见 §12.1。

**抽题的放宽策略**（`drawQuestions`）——题型是学生显式选的，不放宽；行业/难度逐级放宽，**逐层累积补抽**：

```
① 行业 + 难度 + 题型  ── 抽 N 道
        │ 不够
        ▼
② 行业 + 题型        ── 只补「还差的条数」，并排除已抽中的题（id not in）
        │ 还不够
        ▼
③ 仅题型             ── 继续补差 + 排除
        │ 还不够
        ▼
   三层合计一道都没有 → 报错「题库中没有符合所选题型的题目，请更换题型后重试」
```

> ⚠️ **不能写成「第一层命中就返回」**（S1 首版就是这么写的，验证时踩到了）：
> 种子数据里「行为面 ∩ 技术行业 ∩ 初级」只有 1 道，按「命中即返回」会建出**只有 1 道题**的场次
> （学生明明选了 5 道）。**必须逐层补抽到凑够为止** —— 这也是 `selectRandomQuestions` 要有
> `excludeIds`（`Collection<Long>`，Mapper 里 `id not in (...)`）的原因。

三层合计仍不足 `totalCount` 时**不报错**，按实际抽到的数量建场（`total_count` 写实际值），前端提示「本场共 N 题」。

**`session_no` 生成**：`S` + `yyyyMMddHHmmss` + 3 位随机数；`session_no` 有唯一索引，撞号时最多重试 5 次。

**`submitAnswer` 的校验链**（每一步挡一类绕过）：

```
① sessionId / questionId 必填
② 场次必须存在 + 属于当前学生              ← StudentDataScopeUtils.checkOwner
③ 场次必须 status = '1'（进行中）           ← 已完成 / 已中断 / 未开始 一律拒绝
④ 题目必须存在 + question.sessionId = 本场  ← 防止拿别场的 questionId 交叉写入
⑤ answerContent 非空、≤ 5000 字
⑥ answerType 只认 '1'（文字）               ← 阶段一不开放语音 / 视频
⑦ 写库：user_id 取场次归属（不是当前登录用户）、question_content 取题目、status 固定 '0'
   —— 其余字段（score / ai_comment / del_flag / create_by …）前端传了也不采信
```

**「全部答完 → 置完成」的判据**（`syncSessionProgress`）：

```
题目数   = interview_question 里 session_id = 本场 的条数
已答题数 = interview_qa     里 session_id = 本场 的 question_id 去重个数
→ answered_count 回写为「已答题数」
→ 若 已答题数 >= 题目数 且 题目数 > 0：status = '2'、end_time = now、duration = now - start_time
```

去重是必须的：`interview_qa` 支持追问（`is_follow_up = '1'`），同一题可能有多条记录，
按条数统计会把 `answered_count` 算超。阶段一虽然恒为「否」，但判据现在就是对的。

**为什么把「置完成」从 `InterviewQaServiceImpl` 搬到 `InterviewSessionServiceImpl`**：

S3 里 `syncSessionProgress` 只做「置完成」；S4 还要「置完成 **+ 建报告壳**」。
如果让 `InterviewQaServiceImpl` 直接注入 `IInterviewReportService`，「作答服务」就凭空知道了「报告」的存在 ——
语义上不对，而且后续每加一个「完成时要做的事」都要再往作答服务里塞一个依赖。搬进会话服务后：

```
InterviewQaServiceImpl        → IInterviewSessionService   （只负责「刷新进度」）
InterviewSessionServiceImpl   → IInterviewReportService    （负责「置完成 + 建壳 + 写冗余指针」）
InterviewReportServiceImpl    → 只依赖 Mapper
```

单向依赖，没有环，也没有让作答服务承担不属于它的职责。

**`ensureReportShell` 是幂等的**：先按 `session_id` 查一次，有就原样返回，没有才建一条 `generate_status='0'` 的壳。
所以「重复答完最后一题」「补建 S4 之前就已完成的老场次」都不会建出第二条报告。

**`report_id` ⇄ `session_id` 双向引用的落地方式**（对应 §6.2）：

```
interview_report.session_id  ← 权威（报告属于哪场，这个字段说了算）
interview_session.report_id  ← 冗余指针，后端在置完成时一并写
```

指针的写入放在 `ensureReportShell` 里 —— 它是「报告诞生」的唯一入口（答完自动建壳、手工填分补建壳都会走到），
建完壳比对 `session.report_id`，不一致就回写（值相同则不写，省一次 update）。两边永远一致，不会出现「只写一边」。
（最初这段写在 `refreshSessionProgress` 里，导致「手工填分补建壳」这条路漏写指针 —— 见 §12.5 补丁 1。）

**`fillReport` 的校验链**：

```
① sessionId 必填
② 场次存在 + 属于当前学生               ← StudentDataScopeUtils.checkOwner
③ 场次必须 status = '2'（已完成）        ← 没答完不给报告
④ 五个维度都非空、且都在 0 ~ 100 之间
⑤ 没壳先补壳                            ← ensureReportShell
⑥ 白名单写入：五个维度 + totalScore（后端按五维平均，保留两位）
              + summary / weakPoints / suggest（各自校验后入库）
              + generateStatus = '2'、generateTime = now
   —— reportNo / userId / status 前端传了也不采信
```

`totalScore` 由后端算，不采信前端 —— 否则前端可以传「五维都是 30、总分 100」。
`weakPoints` 必须能解析成 JSON 数组，否则直接报错（阶段一存的就是数组，前端拿它当标签渲染）。

### 13.2 4 个外键列的 insert 写法收口（PLAN §5.1 的结论）

**结论：改。** 4 列在 `insert` 里由 `<if test="xxx != null">` 条件列改为**无条件列**：

| Mapper | 列 |
| :--- | :--- |
| `InterviewQuestionMapper.xml` | `session_id` |
| `InterviewQaMapper.xml` | `session_id`、`question_id` |
| `InterviewReportMapper.xml` | `session_id` |

**为什么改**：

1. 这 4 列都是 `NOT NULL` 且无 `DEFAULT`，业务上必填 —— S1~S4 落地后**全部由后端赋值**：
   `insertInterviewSession` 抽题时写 `question.sessionId`；`submitAnswer` 写 `qa.sessionId` / `qa.questionId`；`ensureReportShell` 写 `report.sessionId`。
2. 条件列在语义上**误导**（看起来像可选）；改成无条件列后，与同一个 `<insert>` 里 `user_id` 的既有写法对齐。
3. **fail-fast**：漏传时立刻 `Column 'xxx' cannot be null`（错误码 1048），而不是让 MySQL 报
   `Field 'xxx' doesn't have a default value`（1364）。两种写法都会 500，但无条件列的报错指向更明确。

**为什么安全**：

- `insert` 是**独立语句**，不与 `update` 共用列片段 —— 改动局部，不影响 `update`（`update` 仍不带这几个外键）。
- 4 个外键在**全部** insert 路径上都有赋值（已逐个核对）。
- 唯一受影响的是**后台端的通用 `POST /interview/{question,qa,report}`**：不带外键时会从 1364 变成 1048 ——
  但这两个都是「必然报错」，没有把「本来能成功的请求」变成失败。
