# 学生端对外契约

> 本文件冻结「学生端」对外暴露的接口、权限、数据与菜单边界。
> 三端（学生端 / 后台端 / 企业端）合并时以此为准；学生端不承诺本契约之外的行为。
> 维护人：tong　最后更新：2026-09-22

---

## 一、接口清单

所有接口统一前缀 `/interview`，均需登录，均由 `@PreAuthorize` 做权限校验。

| # | 模块 | 基础路径 | 权限前缀 |
| :- | :--- | :--- | :--- |
| 1 | 学生档案 | `/interview/profile` | `interview:profile:*` |
| 2 | 学生简历 | `/interview/resume` | `interview:resume:*` |
| 3 | 学生岗位画像 | `/interview/jobprofile` | `interview:jobprofile:*` |
| 4 | 模拟面试场次 | `/interview/session` | `interview:session:*` |
| 5 | 面试题目 | `/interview/question` | `interview:question:*` |
| 6 | 面试问答 | `/interview/qa` | `interview:qa:*` |
| 7 | 面试复盘报告 | `/interview/report` | `interview:report:*` |
| 8 | 题库题目 | `/interview/bank` | `interview:bank:*` |

每个模块的端点固定为这 6 个（`{base}` 为上表的基础路径）：

| 方法 | 路径 | 说明 | 对应权限后缀 |
| :--- | :--- | :--- | :--- |
| GET | `{base}/list` | 分页列表 | `list` |
| GET | `{base}/{id}` | 详情 | `query` |
| POST | `{base}` | 新增（JSON body） | `add` |
| PUT | `{base}` | 修改（JSON body） | `edit` |
| DELETE | `{base}/{ids}` | 批量删除，ids 逗号分隔 | `remove` |
| POST | `{base}/export` | 导出 Excel | `export` |

> **题库 `question_bank` 的端点照旧全部保留，但学生端只调用 `list` / `{id}` / `export` 三个。**
> `add` / `edit` / `remove` 的接口与权限标识**都不删除**（后台端要用），学生端只是不渲染入口；
> 「学生」角色没有被授予这三个权限，所以**学生端即使直接调接口也会被 `@PreAuthorize` 拦下**。
> 换言之：**学生端的「只读」是权限层面保证的，不是靠前端隐藏按钮**。三端合并时请保持这个前提。
>
> **另外，题库的 `status` 是「对学生隐藏」的开关**：`list` / `export` 在没有 `interview:data:all` 权限时会强制
> `status = '0'`，`getInfo` 遇到停用记录按「不存在」处理（返回「数据不存在或已删除」）。
> **后台端要管理停用题目，必须持有 `interview:data:all`**，否则也会被这条规则挡掉。
>
> 学生端页面里，「状态」列 / 状态筛选 / 抽屉里的状态**都按 `interview:data:all` 门控** ——
> 学生不渲染（他本来也查不到停用题），持有该权限的账号才渲染，用来识别哪道题被停用了。
> 若后台端另做页面，请沿用**同一个权限点**做门控，保持前后端判据一致。

> **流程四件套的对外行为（2026-09-22 起，S1 已落地场次部分）**
>
> 四个流程模块（`session` / `question` / `qa` / `report`）端点仍是上面这 6 个，但**语义收紧了**：
>
> - `POST /interview/session`（=「开始面试」）**只接受 3 个字段**：`jobProfileId`、`questionType`、`totalCount`。
>   其余字段（`sessionNo` / `userId` / `industry` / `jobName` / `difficulty` / `status` / `startTime` /
>   `totalCount` 实际值 / `reportId`）**一律由后端覆盖生成**，前端传了也会被丢掉。
>   - 响应体由 `{code, msg}` 变为 `{code, msg, data: {id, sessionNo, totalCount, ...}}`，
>     便于前端拿到新建场次的 `id` 直接跳到作答页。**这是 `add` 的例外，其余 7 个模块的 `add` 仍返回 `{code, msg}`。**
>   - 建场时后端会按「行业+难度+题型 → 行业+题型 → 仅题型」**逐层累积补抽**从 `question_bank`
>     （`status='0'`）抽题写入 `interview_question`（`source='2'` 题库抽取、`question_no` 从 1 递增）。
>     每层只补「还差的条数」并用 `id not in` 排除已抽中的题，**累积到凑够 `totalCount` 为止**。
>     三层合计仍不足时**不报错**，`total_count` 写实际抽到的数量（前端提示「本场共 N 题」）。
> - `DELETE /interview/session/{ids}` 会**级联删除**该场的 `interview_question` / `interview_qa` /
>   `interview_report`（按 `session_id`，`@Transactional`）。**题目 / 问答 / 报告三个模块不提供独立的删除入口。**
> - 关联权威性：`interview_report.session_id` 是权威关联，`interview_session.report_id` 是后端写的**冗余指针**。
>   三端都不要出现「只写一边」。
> - 路由串联（前端行为，但三端合并会共用）：`/student/session` 为主干，其余两页靠
>   `?sessionId=x` 下钻；直接点菜单进来时显示空态 + 场次下拉。
>   ⚠️ **2026-09-28 起「面试问答」已并入「面试环节」**：`/student/qa` 路由取消，
>   作答 / 回顾界面挂在 `/student/session?sessionId=x` 下（该页双模式：不带 `sessionId` = 场次列表）。
>   为此动了一次 `sys_menu`：删掉 qa 的 C 型模块菜单、它的 5 个按钮改挂到「面试环节」菜单下。
>   详见 §6 与 `sql/student_qa_merge_menu.sql`。**`interview:qa:*` 权限点一个没少**（后端 `@PreAuthorize` 仍在用）。
> - `interview_question` 学生端**只读**（S2 已落地）：页面靠 `?sessionId=x` 定位一场，
>   不再调用 `add` / `edit` / `remove`（端点与权限标识都保留，学生角色没被授权，`@PreAuthorize` 会拦）。
>   三个接口（`session/{id}`、`question/list?sessionId=`、`qa/list?sessionId=`）都走 `scopeToCurrentUser`，
>   **「我的题目 / 我的作答」是后端按登录用户过滤的**，前端只负责传 `sessionId`。
> - **参考答案的显隐（决策 1）**：判据是 `session.status === '2'` **或** 该题已有 `interview_qa` 记录，
>   列表页与详情抽屉用同一条规则。三端如果也要展示 `reference_answer`，请沿用同一判据。
>   `reference_answer` / `key_points` **没有挂 `@Excel`**，不会从导出接口漏出去。
> - `interview_qa` 学生端**只写不删**（S3 已落地）：`/student/session?sessionId=x` 是唯一有写操作的页面
>   （原 `/student/qa`，2026-09-28 并入「面试环节」），
>   只调用新增的 `POST /interview/qa/submit`；`add` / `edit` / `remove` 端点与权限标识保留给后台端，学生端不调用。
>   - `submit` 只认 `sessionId` / `questionId` / `answerContent` / `answerType` / `duration`；
>     `answer_time`（服务端时间）/ `user_id`（取场次归属）/ `question_content`（取题目）/ `status` /
>     `score` / `ai_comment` 一律由后端写入，前端传了也会被丢掉。
>   - 写入前校验：场次属于当前学生 **且** `status='1'`（已完成 / 已中断 / 未开始一律拒绝）；
>     题目必须真实存在且 `question_id` 属于该场次（防止跨场次写入）。
>   - 同一场次同一题重复提交 = **覆盖**（按 `session_id + question_id + is_follow_up='0'` 定位主作答），
>     阶段一一个题目只有一条主作答记录。
>   - 提交后回写场次进度：`answered_count` = 该场**有作答记录的题目数**（按 `question_id` 去重）；
>     全部题目答完 → 场次置 `status='2'`、写 `end_time`、`duration` = 开始时间到现在。
>   - 响应体为 `{code, msg, data: <作答记录>, session: <场次最新状态>}` —— `session` 让前端不用再发一次请求
>     就能翻到只读模式。**这是 `submit` 的例外，与 `add` 的例外相互独立。**
> - 场次状态流转（S3 已落地）：**没有**改通用的 `PUT /interview/session`，另开 `PUT /interview/session/abort/{id}`，
>   只做「进行中 → 已中断」（写 `end_time` / `duration`），已结束的场次调用会报错；
>   通用的 `edit` 仍保留给后台端做完整 CRUD。
>   - **字段级写权限已堵死（路线 2，2026-09-22）**：学生角色虽然持有 `interview:session:edit` /
>     `interview:qa:add` / `interview:qa:edit` / `interview:report:add|edit|remove`，但**直接调通用
>     `POST / PUT / DELETE /interview/{session,question,qa,report}` 会被 Service 层闸门拒绝** ——
>     闸门是 `StudentDataScopeUtils.requireManage(label)`，判据 `!canViewAll()`，抛
>     `ServiceException("xxx不支持直接编辑，请通过对应页面的业务入口操作")`。
>     若依的权限点粒度做不到「同权限不同字段」，所以这道闸门只能放在 Service 层（详见第五节）。
>     学生的写操作一律走业务入口：开始面试 / 作答提交 / 提前结束 / 手工填分。
>     ⚠️ **三端注意**：这道闸门的判据是 `interview:data:all`。后台端 / 企业端若有角色**不带
>     `interview:data:all`** 却要调用通用 CRUD 做维护，会被误伤 —— 后台侧角色请确保持有该权限点
>     （`user_id=1` 超管天然通过，不受影响）。
> - `interview_report` 学生端**只读 + 手工填分**（S4 已落地）：页面靠 `?sessionId=x` 下钻或直接进列表，
>   不调用 `add` / `edit` / `remove`。
>   - **建壳**：后端幂等建一条 `generate_status='0'` 的报告壳（`report_no` 后端生成、`user_id` 取场次归属），
>     并回写 `interview_session.report_id` 冗余指针。**前端不参与建壳。**
>     建壳的唯一入口是 `ensureReportShell`，两条路都会走到：① 场次置「已完成」时；② 手工填分补建时。
>     指针的写入也收在这里，所以两条路都不会漏写 `session.report_id`。
>   - **补建历史场次**：`fillReport` 对「没有壳的已完成场次」会先补壳再填分，所以学生端可以用它补出
>     S4 之前就已完成的场次的报告 —— 三端若也有存量数据，同样可以借这条路径补。
>   - **手工填分**：`POST /interview/report/fill`（`interview:report:edit`），只认
>     `sessionId` + 五个维度分 + `summary` / `weakPoints` / `suggest`。
>     `totalScore` 由后端按五维平均算（保留两位），`reportNo` / `userId` / `generateStatus` / `generateTime`
>     一律由后端写入 —— 前端传了也会被丢掉。
>   - 写入前校验：场次属于当前学生 **且** `status='2'`（没答完不给报告）；五个维度都非空且都在 0~100；
>     `weakPoints` 必须能解析成 JSON 数组（阶段一存数组，前端当标签渲染）。
>   - 列表查询已 **left join `interview_session`**，多返回 `sessionNo` / `jobName` / `startTime` 三个只读展示字段，
>     并支持 `jobName` 模糊筛选 —— 三端如果也做报告列表，可以直接复用这几个字段，不必自己再 join。
>   - ⚠️ **`fillReport` 是阶段一的演示入口**，阶段三接入 AI 评分后应删除，或把 `interview:report:edit`
>     从学生角色收回（学生不该能给自己打分）。字段级写权限**已由 Service 层闸门堵死**（见上一条），
>     通用 `POST / PUT / DELETE /interview/report` 现在会被 `requireManage("面试复盘报告")` 拒绝。

### 1.1 认证扩展接口（未登录可调用）

学生端的登录方式：**手机号 + 验证码登录**、**手机号/账号 + 密码登录**、注册与找回密码。其中除「账号 + 密码」走若依自带的 `POST /login` 外，其余都是学生端新增的，统一挂在 `/interview/auth` 下。

| 方法 | 路径 | 入参 | 出参 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| POST | `/interview/auth/sms/send` | `{ phone, scene }` | `{ code, msg, mock?, mockCode? }` | 发送短信验证码 |
| POST | `/interview/auth/login/sms` | `{ phone, code }` | `{ code, msg, token }` | 手机号 + 验证码登录 |
| POST | `/interview/auth/register/phone` | `{ phone, code, password, agreed }` | `{ code, msg }` | 手机号验证码注册 |
| POST | `/interview/auth/resetPwd/phone` | `{ phone, code, password }` | `{ code, msg }` | 手机号验证码重置密码 |

**`scene` 取值（必填，验证码按场景隔离）**：`login` / `register` / `resetPwd`。

> ⚠️ **场景隔离是刻意的**：三个场景的验证码在 Redis 里是三个不同的 key，互不通用。否则「登录用」的验证码就能直接拿去重置密码，等于把改密码的门槛降到「能收到短信」。三端如果也做验证码，请沿用这个约定。

**验证码规则**（`AuthCodeConstants`）：

| 项 | 值 |
| :--- | :--- |
| 有效期 | 5 分钟 |
| 发送间隔 | 同手机号 + 同场景 60 秒一次 |
| 每日上限 | 同手机号 + 同场景 10 次 |
| 错误上限 | 连续错 5 次验证码作废，需重新获取 |
| 位数 | 6 位数字（`SecureRandom`，允许前导 0） |
| 一次性 | 校验通过立即作废 |

**短信通道**：配置 `interview.sms.channel`，默认 `mock`。

- `mock`（开发期）：**不真发短信**，验证码写 Redis + 打 WARN 日志。另外配置 `interview.sms.mock-expose-code`（默认 `true`）会把验证码回显在响应里（字段 `mock` / `mockCode`），前端直接展示，省掉翻日志。
  > ⚠️ **上线前必须把 `mock-expose-code` 改成 `false`，并切到真实通道** —— 否则等于把验证码白送给调用方。
- `aliyun`：占位实现（`AliyunSmsSender`），**尚未接入**，切过去调用会直接抛异常（故意失败，避免通道配错却静默以为发出去了）。接入步骤写在类注释里。

**注册出来的账号长什么样**（三端合并时请注意）：

| 字段 | 值 | 原因 |
| :--- | :--- | :--- |
| `user_name` | **手机号** | 这样「账号 + 密码登录」用手机号也能进，用户不用记两套东西 |
| `phonenumber` | 手机号 | 手机号唯一，一个号只能注册一个账号 |
| `nick_name` | `学员` + 手机号后 4 位 | 默认昵称，学生可在个人中心改 |
| 角色 | 配置 `interview.auth.register-role-key`（默认 `student`） | **不绑角色的话新用户登录后一片空白**，所以角色查不到时直接报错而不是静默放过 |

**协议勾选（用户协议 / 隐私政策）**：

- **注册**：服务端强制校验 `agreed === true`（`PhoneRegisterBody.agreed`）。注册是「新建一段法律关系」的动作，不能只靠前端把按钮置灰。
- **登录**：由前端门控（未勾选则抖动提示并阻止提交）。之所以不在 `/login` 上强制，是因为 `LoginBody` 在 `ruoyi-common` 里 —— 动它就成了三端合并的公共层改动，而收益只是多加一个字段。
- 协议正文页：`/agreement/user`、`/agreement/privacy`（前端路由，**未登录可访问**，在 `permission.js` 的 `whiteList` 里）。当前是**占位正文**，上线前需替换。

**依赖的运行时开关**：`sys_config.sys.account.registerUser` 必须为 `'true'`，否则前端不显示注册入口、注册接口直接拒绝。若依官方脚本默认是 `false`，学生端脚本已代为打开（`sql/student_init.sql` 第 6 节 / `sql/student_patch.sql` 第 4 节）。

> ⚠️ **直接改库不会刷新 Redis 参数缓存**（`sys_config:<key>` 没有过期时间）。不过 `SysConfigServiceImpl` 有 `@PostConstruct → loadingConfigCache()`，**重启后端会重新载入**；不重启的话就去「系统管理 → 参数设置」点一次「刷新缓存」。

**实现约束**：这 4 个接口用 `@Anonymous` 标记，靠若依的 `PermitAllUrlProperties` 在启动时自动放行 —— **不需要改 `ruoyi-framework` 的 `SecurityConfig`**，也就不会给三端合并添新的公共层冲突点。同理，取角色 ID 用的是学生端自己的 `StudentAuthMapper.selectRoleIdByKey`，没有动 `ruoyi-system` 的 `ISysRoleService`。

> **一个容易踩的坑**：短信登录**不能**复用 `UserDetailsServiceImpl.loadUserByUsername()` —— 它内部会调 `SysPasswordService.validate()`，而那里要从 `AuthenticationContextHolder` 取「本次登录用的密码」来比对，短信登录压根没有密码，会直接 NPE。正确做法是 `createLoginUser(SysUser)`（public，只装配权限，不做密码校验），并自己补上「账号是否停用」的检查。

## 二、权限标识

- **每模块 6 个**：`list` / `query` / `add` / `edit` / `remove` / `export`，共 8 × 6 = 48 个。
  - ⚠️ **挂载位置有讲究**：其中 `list` 平时挂在 **C 型模块菜单**上，另外 5 个才是 F 型按钮。
    所以 **删掉一个模块的 C 型菜单 = 删掉该模块的 `:list` 权限点**。删之前先 grep 后端
    `@PreAuthorize`，确认没人在用（2026-09-28 踩过：删「面试问答」菜单把 `interview:qa:list`
    一起删了 → 学生 403）。
  - 例外：`interview:qa:list` 因「面试问答」并入「面试环节」，已降级成 F 型按钮（见 §6）。
- **全量数据权限点**：`interview:data:all`
  - 语义：拥有此权限可查看与操作**全部**学生的数据（不受 `user_id` 隔离限制）。
  - 分配对象：只给后台管理角色；**不要**分配给「学生」角色。
  - 超级管理员无需分配——若依对 `user_id = 1` 自动授予 `*:*:*`，天然通过。
  - 注册脚本：`sql/student_init.sql` 第 2 节（原始出处 `ruoyi/dataScopePermiMenu.sql`）

### 3.1 新手引导与 `student_profile.guide_status`

`student_profile.guide_status`（字典 `student_guide_status`）是**系统维护字段** —— 学生档案表单的白名单里不含它（见 `src/views/interview/profile/index.vue` 的 `EDITABLE_FIELDS` 注释）。它由**新手引导流程**在结束时写入：

| 项 | 值 |
| :--- | :--- |
| 触发点 | 学生走完引导第 5 步「引导完成」 |
| 调用 | `PUT /interview/profile`，请求体只有 `{ id, guideStatus: '1' }` |
| 前端封装 | `src/api/interview/profile.js` → `finishGuide(id)` |
| 前置 | 档案与学生账号 1:1；没有档案时先 `POST /interview/profile`（带 `nickname`）建一条，再取回 id |
| 所需权限 | `interview:profile:edit` / `interview:profile:add`（学生角色已有） |
| 归属校验 | 走 `StudentDataScopeUtils.checkOwner`，学生只能改自己的档案 |

引导流程**不新增表、不新增后端接口**，只是把已有业务表串起来：

- 岗位画像（行业 / 岗位 / 难度）与目标企业（企业类型）**落在同一条 `student_job_profile`**（`industry` / `job_name` / `difficulty` / `company_type`）
- 简历落在 `student_resume`（`source_type = '1'` 本地上传）
- 引导状态落在 `student_profile.guide_status`

前端入口：路由 `/guide`（`name = 'StudentGuide'`，`hidden: true`，全屏、不进侧边栏）。首页 `views/index.vue` 在 `guide_status != '1'` 时自动跳转；「跳过引导」只写本机 localStorage（`interview_guide_dismissed` / `interview_guide_done`），**不改库**，首页入口仍然保留。

### 3.2 学生端首页（`views/index.vue`）

首页**不新增表、不新增后端接口**，用已有的 list 接口 + 2 个派生查询拼出来。三端若也要做首页，可直接复用下面这套查询。

| 首页数据块 | 查询 |
| :--- | :--- |
| 等级 / 积分 / 引导状态 | `GET /interview/profile/list?pageNum=1&pageSize=1` |
| 继续面试 / 历史练过的岗位 | `GET /interview/session/list?pageNum=1&pageSize=20&orderByColumn=id&isAsc=desc` |
| 最近报告（得分 + 五维） | `GET /interview/report/list?pageNum=1&pageSize=1` |
| 目标岗位（岗位推荐基准） | `GET /interview/jobprofile/list?pageNum=1&pageSize=20&status=0` |
| 真题范例（高频真题） | `GET /interview/bank/list?pageNum=1&pageSize=3&source=1&orderByColumn=useCount&isAsc=desc` |

> **`orderByColumn` / `isAsc` 是若依 `startPage()` 自带的分页排序能力**（`PageDomain.getOrderBy()` → `StringUtils.toUnderScoreCase` → 拼 `order by use_count desc`，并有 `SqlUtil.escapeOrderBySql` 做白名单转义）。**用它不需要改任何后端代码**，三端都能用。
> ⚠️ 例外：`interview_report` 的 list 语句里**已经写死** `order by ir.id desc`，再传 `orderByColumn` 属于重复排序，**不要传**。

#### ⚠️ 首页必须按 `userId` 过滤成「只看自己的」

`StudentDataScopeUtils.scopeUserId()` 对带 `interview:data:all` 的身份返回 `null`（即查询不限定 `user_id`）。所以 **admin / 后台端身份登录时，上面 4 个带 `user_id` 的 list 返回的是「全部学生的行」**（2026-09-28 实测：admin 登录，`profile/list` 返回的是 `userId=103` 即 student01 的数据）。

因此首页拿到列表后**必须再按 `row.userId === 当前登录用户 id`（`useUserStore().id`）过滤一遍**：

- 学生端：后端已限定范围，过滤是**空操作**；
- 管理员：只看自己的行，没有就显示空态。

**不能**用「按 `interview:data:all` 整块隐藏这些数据块」来代替 —— 那样管理员首页会只剩公共内容（此方案实现过，已否掉）。

#### 两个前端启发式（阶段三由 AI 替换）

1. **等级推导**：`student_profile.current_level` **目前没有字典、也没有任何后端代码写它**（DDL 默认值 `'小白'`）。首页按 `current_points` 推导等级（六级：面试小白 / 初出茅庐 / 渐入佳境 / 对答如流 / 面试达人 / 面霸）；只有当 `current_level` 被写成了阶梯以外的值时才以库里的为准。
   ⚠️ **这是共享面上的一个待定项**：如果后台端 / 企业端以后要写 `current_level`，**需要先约定值域并建一个字典**（建议 `student_level`），否则三端各写各的，同一个字段会出现几套语义。
2. **薄弱点 → 题型映射**：取最近一份**生成成功**（`generate_status='2'`）的报告里五维得分最低的一项，按下表映射到 `interview_question_type` 推题。

   | 维度 | 题型 |
   | :--- | :--- |
   | 完整性 `score_completeness` | `1` 行为面 |
   | 逻辑性 `score_logic` | `4` case 面 |
   | 流畅度 `score_fluency` | `3` HR 面 |
   | 深度 `score_depth` | `2` 技术面 |
   | 自信度 `score_confidence` | `3` HR 面 |

### 4.2 三端合并时请注意

1. 这 13 个 `dict_type` 属于**共享面**。其他端要用同样的枚举，请**复用同一套 `dict_type` 与值域**，不要另建一套「名字一样、值不一样」的字典。
2. 若依的 `sys_dict_type.dict_type` 是**唯一索引** —— 同名会直接插入失败。想加值就往已有的 `dict_type` 里补 `sys_dict_data`。
3. 其他端如需新枚举，请用**独立前缀**（后台端 `admin_*`、企业端 `corp_*`），避免与 `student_*` / `interview_*` 冲突。
4. 字典值域一旦有业务数据落库，**改值（不是改标签）就等于数据迁移**。所以新增枚举值时请**追加**，不要重排已有值。

## 五、数据隔离规则

统一入口：`com.ruoyi.interview.utils.StudentDataScopeUtils`

| 方法 | 用途 | 全量权限持有者 | 普通学生 |
| :--- | :--- | :--- | :--- |
| `canViewAll()` | 是否有全量权限 | `true` | `false` |
| `currentUserId()` | 取真实登录用户 ID（写入归属用） | 真实 ID | 真实 ID |
| `scopeUserId()` | 查询范围（`null` = 不限制） | `null` | 本人 ID |
| `bindOwner(record)` | 新增时强制写 `user_id` | 写自己 ID | 写自己 ID |
| `scopeToCurrentUser(query)` | 列表 / 导出限定范围 | 不限制 | 限本人 |
| `checkOwner(record, label)` | 详情 / 修改 / 删除校验归属 | 跳过校验 | 不一致抛异常 |
| `requireManage(label)` | **字段级**写闸门：通用 CRUD 是否放行 | 放行 | 抛 `ServiceException` |

配套约定：
- 领域类实现 `com.ruoyi.interview.domain.UserOwned` 接口（`getUserId` / `setUserId`）。
- Mapper XML 的 `selectXxxList` 的 `<where>` 内必须有 `<if test="userId != null"> and user_id = #{userId}</if>`。
- `insert` 的 `user_id` 是**无条件列**，不用 `<if>` 包裹——漏设时会立刻报错，而不是被静默丢弃。
- `update` 语句里**不含** `user_id`，防止改数据归属。
- `insert` 里的**业务外键列也是无条件列**（S5 收口）：`interview_question.session_id`、`interview_qa.session_id` / `question_id`、
  `interview_report.session_id`。这 4 列 `NOT NULL` 无 `DEFAULT` 且业务必填，无条件列能在漏传时立刻报 1048，而不是等 MySQL 报 1364。
  ⚠️ 后台端调通用 `POST /interview/{question,qa,report}` 时**必须**带这几个外键。

**字段级防线（`requireManage`，2026-09-22 补）**

记录级防线（上表）解决「能不能碰这条记录」，字段级防线解决「能不能改这条记录的系统字段」。
通用 CRUD 端点（`POST / PUT / DELETE /interview/xxx`）是给后台端做完整维护用的，字段**没有白名单**，
学生调它就能绕过业务入口改系统字段（如 `status` / `score` / `ai_comment` / `total_score`）。
若依的权限点粒度做不到「同一权限点、不同字段」，所以闸门放在 Service 层：

| 模块 | 加了闸门的通用写方法 | 不加闸门的业务入口 |
| :--- | :--- | :--- |
| `interview_session` | `updateInterviewSession` | `insertInterviewSession`（开始面试）、`deleteInterviewSessionByIds`（删场次·级联）、`abortInterviewSession`、`refreshSessionProgress` |
| `interview_question` | `insert` / `update` / `deleteByIds` / `deleteById` | ——（S2 起学生端只读，无业务入口） |
| `interview_qa` | `insert` / `update` / `deleteByIds` / `deleteById` | `submitAnswer`（作答提交） |
| `interview_report` | `insert` / `update` / `deleteByIds` / `deleteById` | `ensureReportShell`（建壳）、`fillReport`（手工填分） |

**判据是 `canViewAll()`**：持有 `interview:data:all` 的角色即后台侧，不受限制。
⚠️ 后台端 / 企业端若有角色不带 `interview:data:all` 却需要通用 CRUD，会被这道闸门误伤 —— 请确保持有该权限点。

### 6.1 路由名（`route_name`）必须全局唯一

后端 `SysMenuServiceImpl.getRouteName()` 的规则是：**`route_name` 为空时取 `path` 并首字母大写**，作为前端路由名。

学生端踩过一次坑（2026-09-28 修复）：

| 菜单 | path | 生成的路由名 | 撞上了谁 |
| :--- | :--- | :--- | :--- |
| 学生档案 | `profile` | `Profile` | 前端内置路由 `/user/profile`（个人中心，name 也是 `Profile`） |

前端 `store/modules/permission.js` 用 `router.addRoute()` 注册动态路由，**vue-router 4 遇到同名路由会先移除旧路由**。于是个人中心被顶掉，点右上角头像「个人中心」→ 落入 404 兜底路由。顺带还会让「首次登录强制改密码」的 `router.push({ name: 'Profile' })` 跳到学生档案。

**约定**：新增菜单时，若其 `path` 首字母大写后与前端内置路由名相同，**必须显式配置 `route_name`**。前端内置路由名全集：

```
constantRoutes : Index, Profile, StudentGuide, ForgetPwd, AgreementUser, AgreementPrivacy
dynamicRoutes  : AuthRole, AuthUser, Data, JobLog, GenEdit
```

已配置：`学生档案` → `route_name = 'StudentProfile'`（URL 仍为 `/student/profile`，路径与权限标识均不变）。
前端对应组件 `src/views/interview/profile/index.vue` 的 `<script setup name>` 同步为 `StudentProfile` —— keep-alive 按**组件名**匹配，须与路由名一致。

反向也要守：**前端新增内置路由时，名字不能撞上菜单生成的路由名**。2026-09-28 新增的新手引导走的就是这条路 —— `/guide`（`name = 'StudentGuide'`，`hidden: true`，不进侧边栏），它占用 `StudentGuide` 这个名字，后续任何菜单的 `path`/`route_name` 都不能再解析成 `StudentGuide`。

自查 SQL（两个查询都应返回 0 行）：

```sql
-- ① 菜单之间路由名重复
select rn, count(*) from (
  select concat(upper(left(coalesce(nullif(route_name,''),path),1)),
                substring(coalesce(nullif(route_name,''),path),2)) as rn
  from sys_menu
  where menu_type in ('M','C') and path is not null
    and path <> '' and path <> '#' and path not like 'http%'
) t group by rn having count(*) > 1;

-- ② 与前端内置路由名撞名
select menu_id, menu_name, path, route_name from sys_menu
where menu_type in ('M','C')
  and concat(upper(left(coalesce(nullif(route_name,''),path),1)),
             substring(coalesce(nullif(route_name,''),path),2))
      in ('Index','Profile','StudentGuide','ForgetPwd','AgreementUser','AgreementPrivacy',
          'AuthRole','AuthUser','Data','JobLog','GenEdit');
```

## 九、共享接口的已知缺口（`/common/upload`）

学生端「学生简历」模块需要文件上传，用的是若依自带的 `/common/upload`。**实测该接口只返回**：

```json
{ "fileName": "...", "newFileName": "...", "originalFilename": "...", "url": "..." }
```

**不含文件类型（`fileType`）与文件大小（`fileSize`）** —— 而 `student_resume` 表里恰好有 `file_type` / `file_size` 两列。

**学生端目前的处理（不改公共层）**：

| 列 | 处理 |
| :--- | :--- |
| `file_type` | 前端从 `url` 后缀推导（`resolveFileType()`），学生不手填 |
| `file_size` | **阶段一不做**：不显示、不提交，库里 `DEFAULT 0` 保持不动 |

**⚠️ 三端请注意**：该接口位于 `ruoyi-common`，属三端共享面。后台端 / 企业端大概率也会遇到同一缺口。
**如果某一端要扩展它的返回体，请先在三端之间对齐**，不要单方面改 —— 否则合并时会出现「同一接口两套返回结构」。

**若将来确实要补 `file_size`**：正确路径是三端共同约定后统一扩展返回体（例如在 `FileUploadUtils` 的返回里补 `fileType` / `fileSize`），
而不是各端在自己页面里绕开。
